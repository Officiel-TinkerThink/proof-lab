# Receipts: decisions and limits

The Node driver (`src/prove.js`, `src/chain.js`) is the only supported driver. The Go driver (`proof-lab-go`) is frozen:
no further changes, and its uncommitted working-tree changes are not part of any release.

## Running

```
node src/prove.js --key-file <path> [--url <http://...>] [--bug <name>] [--receipts <dir>]
node src/prove.js --verify --key-file <path> [--receipts <dir>] [--expect-head <hash>]
```

Exit codes: run 0 PASS, 1 FAIL, 2 ERROR (cannot tell). Verify 0 intact, 1 tampered or unsigned, 2 cannot verify.

## Key

- The key comes only from `--key-file`. The file must be mode 0600 or stricter (POSIX). Its contents are at least 32 bytes.
- `PROOF_LAB_KEY` in the environment is refused: the run and the verify exit 2 before any receipt is written. Deleting a
  variable does not remove it from `/proc/<pid>/environ`, so the only real fix is to unset it in the shell.
- The key is generated by a cryptographically secure generator (for example `openssl rand -base64 48`). The code checks
  length, not entropy.
- Key custody and delivery are owned by the operator's secret manager. Write the key file for each run; do not commit it.

## Chain

- One chain per receipts directory, one key. A key change does not start a new chain: a new chain would let an earlier
  segment be removed without detection. Verification needs the key that signed each receipt, and the verifier reports a
  receipt signed under another key by its `keyId`.
- A new receipt must sort after the chain head (by file name, which is the timestamp). A receipt that does not is refused,
  so the chain cannot fork. Repeat the run to get a later timestamp.
- The head is anchored outside the receipts directory with `--expect-head`. The anchor store must be written by someone
  other than the operator, because a writer who controls the directory can rewrite it. Choosing that store is a QMS decision.

## Writes and locks

- Each receipt is written to a temp file, flushed, renamed over its name, and the directory is flushed (POSIX). Written
  receipts are set read-only (0444).
- Writers hold `.chain.lock` (exclusive create, holding `{pid, host}`) around the head read and the write.
- `run` and `prove` stamp a receipt's `at` inside the lock, as it joins the chain, so runs that overlap (in one process or
  several) never refuse each other. Two seals in one millisecond would share a stamp, so a head up to one second ahead is
  waited out; a head further ahead is a clock problem and the write is refused, as before.
- A lock is reclaimed only when its owner is provably gone: same host and the pid no longer exists. A lock held by a live
  process or by another host is never taken over, by age or otherwise; the writer waits, then fails and names the file.
- Known limits: a pid can be reused after a crash, so a stale lock can look live until the pid is reused. Two reclaimers
  racing on the same stale lock can, in a narrow window, remove a fresh lock.

## Power-cut test (guest level)

Scripts: `test/power/`. The test boots a Debian bookworm guest under KVM, writes receipts through `src/chain.js` inside the
guest, and prints `ACK <index>` only after `writeReceipt` resolves (file and directory flushed). The host kills the VM at a
random point mid-write (a power cut: no guest shutdown). A second boot runs `verifyChain` on the same disk. The invariant:
every ACKed receipt is present after the cut (verified head >= last ACK) and the chain has no problems.

- Needs: Linux host with `/dev/kvm`, QEMU, `debootstrap`, `e2fsprogs`, Node 24 on the path, root in the container.
- `build-image.sh` builds the guest (rootfs, kernel, Node, `chain.js`) into an ext4 image. `SRC` and `W` select the source
  and the output directory.
- `host-run.sh` runs the cycles. `RUNS` sets the count; `W` selects the image directory; `CACHE` sets the QEMU cache mode
  (default `none`, which bypasses the host page cache).
- The guest init waits 30 s after requesting power-off, and each QEMU boot has a 240 s timeout (a guest that panics on
  exit must not hang the driver).
- Control: the same driver against a copy of `chain.js` with both flush calls removed. It must fail; it proves the test
  detects a missing flush.

Result (2026-10-19, five cycles each, final driver):

| Image | Cycles | Result |
|---|---|---|
| Baseline (fsync file and directory) | 5 | 5 PASS: every cut verified; verified head >= last ACK; 0 problems |
| Control (no flush) | 5 | 5 NOT-DURABLE: after the cut `/work/receipts` was missing, so acknowledged receipts were lost |

Limits: QEMU is killed, so the host's page cache survives. This shows the guest flush path, not host power loss.
Earlier runs were invalid (guest init PATH, a VM that hung on power-off, a driver race on CRLF output) and are not reported.

## Limits not covered by tests

- **Windows directory flush.** Node cannot open a directory to flush it on Windows, so a rename is not flushed there. The
  file itself is flushed before the rename. This is recorded as a residual risk.
- **Power loss at the host.** Not tested. The guest-level power-cut test below covers the guest's flush path. A host-level
  attempt on 2026-10-19 used dm-flakey under ext4 in WSL: its self-test passed, but the no-flush control also passed, so
  the harness does not separate durable from non-durable writes, so its baseline result is not evidence. Diagnosis: the
  table swap that sets the cut (`dmsetup resume`) coincides with the dirty page cache being written to the device, so the
  unflushed receipts reach the disk before the cut takes effect. Dropped writes were confirmed for fsynced data (0 of 50
  survived). A discriminating test needs a flush-aware record-and-replay device (dm-log-writes), not a table swap. The WSL
  changes were reverted. Status: blocked on this machine. The WSL2 kernel has no `CONFIG_DM_LOG_WRITES`, so the test needs
  a Linux host with dm-log-writes (or another block-level fault injector). Until it runs there, host power loss is an
  accepted residual risk for the QMS owner to accept or assign. Run a discriminating host-level test before any validation use.
- **Windows read-only attribute.** Only the write bit maps to the read-only attribute on Windows, so 0444 does not stop the
  file's owner. The code clears the flag before it removes a file it wrote (`discard`), and does not rely on the Node
  unlink branch for that. The Windows path is not exercised by the Linux container tests.
- **Key file mode on Windows.** The 0600 check is POSIX only, and its test is skipped on Windows. Windows does not enforce it.
  Store the key file where only the operator's account can read it (NTFS ACL on the user profile). The owner accepted this
  residual risk on 2026-10-19.
- **Cross-driver locking.** The Go driver used `flock` on the same file name. Since Go is frozen, no other driver writes this chain.
